01 - Problem & solution

Nobody knew a load was stuck until the customer called

Problem: ops monitors assigned and in-transit loads by repeatedly going through a live database - every check starts from zero, and there is no definition of what is normal versus an incident.

Solution: A watcher that tells us "What status is the truck currently in, what status should happen next, when should it happen, has it happened, and does Operations need to intervene?".

No repetitive manual checks| Less human error at scale| Consistent judgment, no bias involved| Memory of what's normal, not a blank slate every time
Deterministic core

Canonical status, ETA, five flags. Pure code, no LLM.

Investigator agent

Claude triages a load only once a flag has fired - noise or real problem?

Report agent

One ranked report per batch - attention queue, load evaluations, recommended actions.

Runs only after a flag fires - a healthy load never costs an LLM call.

03 - Live demo

Now, the watcher working live

Switching to the terminal - running one full wake against a live batch of loads.

  1. List the batch - console prints the active load IDs from ops.
  2. Per-load evaluation - a load that stays quiet next to one that fires a flag.
  3. Investigator firing - severity and latency for that call, live.
  4. Close-out - a load that completes this wake and drops into fleet memory.
  5. Report write - open report.html, walk the attention queue.

How a recommended action is chosen

Every firing incident starts with a deterministic action tag - no LLM. The investigator can only replace it.

IncidentDeterministic fallback
Transition overdueCHECK_STATUS_WITH_CARRIER
Commitment riskESCALATE_CUSTOMER_COMMITMENT
Stale GPSVERIFY_TRACKER
Status–GPS conflictVERIFY_LOCATION_VS_STATUS
Dropoff riskNOTIFY_CUSTOMER_OF_RISK

The LLM only overrides this when it has something more specific to say. If the investigator ran and rated the load ELEVATED or CRITICAL, its own plain-language recommended_action (who to call, what to check) replaces the generic tag for that incident.

05 - LLM cost & guardrails

Making the LLM layer trustworthy, not just capable

The deterministic core is the source of truth by design. What happens when the LLM layer goes wrong?

Guardrails already in place

01
Forced structured output

Both agents are forced to call a fixed-schema tool - no free-text output reaches the report.

02
Findings retained internally, never dropped

A suppressed finding for a firing flag still exists in the incidents table.

03
The deterministic core is untouchable

The investigator only interprets and labels a flag - it can never change whether it fired, delete it, or alter canonical status.

04
Deterministic fallbacks handle failures

Any exception, missing key, or bad tool call falls back to deterministic path to the output. The wake continues either way.

Cost & time

Every LLM call is recorded per batch - agent, model, latency, input/output tokens.

MetricTracked how
LatencyTime taken per call, averaged across the batch

06 - Deep dive

Looking under the hood

Exact logic for the calculations.

How ETA is actually calculated

01
Straight-line distance

Haversine distance between the latest GPS ping and the target - using latitude and longitude coordinates.

02
Road factor

Straight-line distance × ROAD_DISTANCE_FACTOR (1.3) - a fixed multiplier approximating real road distance over highway straight-line.

03
Speed, with a floor

Uses the GPS-reported live speed if it's at least MIN_ETA_SPEED_KPH (25 km/h); otherwise falls back to a flat DEFAULT_SPEED_KPH (40 km/h).

04
Hours to arrival

Road distance ÷ speed = hours; added to now for forecasted. If GPS or target coordinates are missing, ETA stays unset - never a guess.

Worked example
Straight-line to dropoff340 km
× road factor (1.3)442 km
Live speed reported8 km/h → below floor, use 40
Hours to arrival442 ÷ 40 = 11.05h

How severity is computed

Two layers - a numeric score and a categorical judgment - feeding one ranked queue.

01
Deterministic score - _severity()
  • Where: report_agent.py, every load, every wake - runs whether or not the investigator did.
  • Computation: weighted point sum - investigator rank if it ran (CRITICAL 400 / ELEVATED 300 / WATCH 200 / CLEAR 0) + commitment BREACHED +100/AT_RISK +80 + dropoff risk +70/+60 + conflict +50 + overdue +60 + stale GPS +30 + unmapped +20 + +5 per open incident.
  • Used for: sorting the attention queue, highest first - before the report-writing model ever sees the batch.
02
Investigator's judgment - overall_severity
  • Where: investigator.py, only once a flag has fired.
  • Computation: Claude reads the flag(s), clocks, and calibrated carrier/lane/shipper history, returns CLEAR | WATCH | ELEVATED | CRITICAL - bounded by hard rules (BREACHED forces a CRITICAL floor; STALE_GPS alone can't reach ELEVATED).
  • Used for: the severity pill on each card. The LLM's job is prose, not ranking - it never re-sorts the queue the score above already ordered.
07 What's next

Where this could go next

The watcher has a wide scope of enhancements, some worth mentioning at this very stage.

Keep the truck honest about its route

  • Route deviation checks - every load runs on a fixed, contracted route - use waypoints to ensure we're not billed extra.
  • Loaded vs. empty miles - track which miles are actually carrying freight, not just whether the truck is moving.
  • Minimum daily progress - an in-transit truck is expected to cover a minimum distance per day (350km).

Give incidents more judgment, not just a fixed rule

  • Explain idle time - Have the agent reason about why: a short break, a long break, waiting on payment, a held load, or a breakdown.
  • Let the agent judge dropoff risk - the delay cascade uses a fixed time window today; introduce agentic judgment.
  • Notice a rescheduled appointment - if ops reschedules a commitment because of the watcher's own recommendation, the next report should recognize that instead of comparing against the now-stale original time.

Learn patterns instead of only tracking named ones

  • A pattern-discovery agent - today the watcher only recognizes patterns it's explicitly told to look for. An agent could find repeated problems across customers, lanes, shippers, and carriers on its own.
  • Model patterns as a graph - rather than flat per-lane stats, relationships between lanes, carriers, and shippers can actually be queried.

See the load, not just its data

  • Hyperlink load ids - straight to the record in the ops DB, so ops doesn't have to go look it up separately.
  • An actual map view - show the load's real position and distance covered, not just a state-based timeline.
  • Cross-check ETA with FASTAG - the expected time between two known toll pings is a second, independent ETA signal alongside the GPS-based one.

Scale up and close the feedback loop

  • Parallelize the investigator - concurrent calls instead of one sequential loop.
  • Explore GraphRAG or Celery for richer cross-load context and orchestration at fleet scale.
  • Positive incidents - track and report successful outcomes, not just failures.
  • A real feedback loop - record what ops actually did with a recommendation, to improve future ones.

Appendix

Reading the real data

Real-world data rarely means what the docs say it means. Four genuine ambiguities in the ops schema, and the deterministic rule each one settled into.

What's the actual difference between a stop's planned arrival, its committed appointment, and its actual arrival?
Resolved with ops directly - three genuinely different clocks, modeled separately rather than collapsed into one "ETA."
Ops has many raw status / sub-status combinations across systems - which ones actually map to our six canonical states, and what happens to one we've never seen before?
Resolved with an explicit STATUS_MAP. Anything unrecognized falls to evidence_state = UNMAPPED_STATUS rather than guessing a canonical state.
FASTAG pings sit in the same table as live telematics - but they aren't the same kind of signal.
Excluded from anything time-sensitive - marks evidence unavailable, never stale.
The LOADED milestone barely shows up in load_tender's own status fields - ops usually jumps straight to en-route-dropoff there.
STATUS_MAP now also reconciles a dedicated status_event LOADED signal alongside tender/sub_status, taking whichever mapped source is furthest along - so a genuine LOADED event is no longer just tolerated as a jump, it's detected directly.

How each flag is actually computed

Exact conditions for evaluating flags as set in flags.py.

FlagCondition

Status–GPS conflict

The same "truck is near pickup" GPS reading means something different depending on what the status already claims:

Active stateConflict fires when

How the delay cascade (domino effect) is computed

Runs every wake as its own deterministic step, independent of which flags already fired - so it also catches a slip building up before any single-row flag would trip. Lives in domino.py, as propagate_delay(state_rows, times, active_row, eta, now).

01
Delay off the active row

Reference time is actual → live ETA → now, first one available. delay = max(0, reference − active_row.planned), in minutes. Below DOMINO_MIN_SLIP (30 min) the cascade stops here - SAFE, nothing propagated.

02
Roll forward onto downstream states

Every incomplete row after the active one has its planned time shifted by that same delay - a rigid shift, v1. No per-row slack is subtracted yet.

03
Compare projected dropoff to the commitment

dropoff_slip = projected[ENROUTE_DROPOFF] − committed_dropoff, in minutes. Zero or negative means on time or early.

04
Verdict

SAFE (slip ≤ 0), AT_RISK (slip within DROPOFF_RISK_MARGIN, 60 min), BREACH_LIKELY (beyond it), UNKNOWN if either time is missing. AT_RISK / BREACH_LIKELY is what sets the DROPOFF_RISK flag and records which downstream states are affected.

Worked example
Active row (AT_PICKUP) plannedSep 9, 6:00 AM
No actual yet - live ETASep 9, 8:30 AM
Delay150 min (> 30 min floor)
ENROUTE_DROPOFF planned → projectedSep 9, 6:00 PM → 8:30 PM
Committed dropoffSep 9, 7:00 PM
VerdictBREACH_LIKELY

Once a load is DROPOFF_RISK, the investigator is handed the whole projected journey and asked to name the affected states, restate the verdict in minutes, and give 2-3 concrete preventive actions plus a customer-facing alert line - shown together as the report's delay cascade block, on both the load evaluation and the journey diagram.

Both calls default to the same model, claude-sonnet-4-6, set once in code and overridable per run via a REPORT_MODEL env var - no separate tuning per agent. A mid-tier Sonnet was picked over a larger model because both jobs are bounded and structured (one fixed tool schema, a JSON context already assembled deterministically) rather than open-ended reasoning, and both run repeatedly - once per flagged load, once per wake - so latency and cost compound; Sonnet is reliable at forced tool-calling and calibrated judgment calls (noise vs. genuine concern) at a fraction of the cost of a top-tier model, with room to swap in a larger one for either agent later without any code change.

Investigator's system prompt, in five instructions

01
Judge each fired flag

Genuinely concerning, or normal occurence for this carrier/lane/shipper's own history? Suppress it if it's noise.

02
Assess overall severity

CLEAR / WATCH / ELEVATED / CRITICAL - a BREACHED commitment forces a CRITICAL floor; STALE_GPS alone can never reach ELEVATED.

03
Narrate every unsuppressed finding

Plain language, one narrative per finding that isn't noise.

04
Recommend a specific action

Who calls whom, what to check - once severity is ELEVATED or above. A short monitoring note otherwise.

05
Reflect on the whole journey when dropoff is at risk

Name the affected downstream states, restate the verdict in minutes, give 2-3 concrete preventive actions.

Report agent's system prompt, in four instructions

01
Write for a two-minute read

Group similar issues, present them bulleted - never a per-load prose dump.

02
Prefer the investigator's own words

overall_severity, finding narratives, and recommended_action over raw flag names, whenever it ran.

03
Never re-rank

Preserve the severity order it's handed (CRITICAL, then ELEVATED, then WATCH) - its job is prose, not ranking.

04
Fall back to a documented flag order

BREACHED → CONFLICT → OVERDUE → AT_RISK → STALE, on loads the investigator never triaged.

Both prompts open with the same constraint: shadow-mode only - recommend actions, never claim anything was updated in the ops system, and use only facts already present in the JSON context handed to them.
